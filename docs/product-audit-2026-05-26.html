Bottom Line

Lionheart has a lot of real product built. IT and maintenance are not empty shells. They include ticket queues, assignment, status changes, devices, assets, QR codes, preventive maintenance, knowledge base, analytics, and reporting.

The biggest problem is not lack of features. The biggest problem is proving reliability. The automated smoke and end-to-end tests are partly broken, performance is below target in many areas, and accessibility issues are showing up on important pages.

Plain-English judgment: the product is broad and useful, but it needs a hard stabilization pass before you can confidently say every section works together under real school-day use.

Critical Findings

1. The smoke-test safety net is broken.

The campus and inventory smoke tests still try to create users with old fields like role and teamIds. The current schema uses roleId and team membership rows. These tests fail before they test the product.

Why it matters: you cannot trust “smoke tests passed” until these scripts are updated. This is especially risky for database and permission changes.

Fix: repair smoke user creation, make all smoke scripts use SMOKE_BASE_URL, and add IT and maintenance smoke tests as first-class scripts.

2. End-to-end API tests are not reliable right now.

The Playwright API suite failed. Some failures came from login returning 500 after a production build ran while the dev server was active. That exposed a workflow problem: building and testing against the same .next folder can break the running dev server.

Why it matters: the API tests should be the strongest proof that auth, security, validation, and ticket CRUD are safe. Right now they are not giving a clean signal.

Fix: run E2E tests against a clean started server, not a dev server that is also being rebuilt. Add a dedicated test:e2e:local script that controls the server lifecycle.

3. Dev-mode performance numbers were misleading.

The wide API speed test hit more than 55 endpoint groups. The stale/broken endpoint failures were fixed, but many p95 targets still missed under heavy local dev load.

A cleaner production-mode benchmark told a different story. Focused checks for settings users, inventory, planning seasons, maintenance knowledge base, events, roles, calendars, and notifications were all fast.

Fix: keep using production-mode benchmarks for speed decisions. Use the broad dev sweep only as a warning map, not as final proof.

4. Some page bundles are still large, but daily pages improved.

The first page-weight passes split heavy drawer/config/detail code away from the first screen. IT, maintenance, dashboard, athletics, calendar, event detail, event day-of, form builder, and Events Hub are lighter now:

  • /it: about 535 kB before, 241 kB after
  • /it/admin: about 266 kB before, 173 kB after
  • /maintenance: about 522 kB before, 238 kB after
  • /dashboard: about 402 kB before, 265 kB after
  • /athletics: about 293 kB before, 181 kB after
  • /calendar: about 358 kB before, 170 kB after
  • /events/[id]: about 601 kB before, 175 kB after
  • /events/[id]/dayof: about 318 kB before, 165 kB after
  • /forms/[id]/builder: about 420 kB before, 110 kB after
  • /events: about 308 kB before, 254 kB after

The event detail pass also fixed an AI status-summary request that returned a browser-visible 500/503 when Gemini was unavailable. It now returns a clean unavailable state.

Why it matters: IT and maintenance workers often use mobile devices in the field. Large bundles hurt load time and battery life.

Fix: keep applying this pattern to any remaining page that crosses about 300 kB first load.

5. Accessibility issues are present on important pages.

The automated browser audit found serious issues such as low color contrast, focusable elements hidden from assistive tools, unnamed progress bars, and an unnamed button on mobile IT.

Why it matters: staff may rely on keyboard navigation, screen readers, or high contrast. These issues also hurt general usability.

Fix: fix all axe issues on dashboard, IT, maintenance, messaging, tickets, inventory, and mobile screens before adding more UI.

Security And Multi-Tenant Risk

The architecture check passed, and the route inventory shows that many handlers are guarded. That is good.

However, the inventory also reported 191 logged-in handlers with no permission decorator. Some may be fine, but this needs review. The report should not assume they are safe without checking each route.

There are also many uses of rawPrisma in API routes. Some are expected, such as auth, public links, webhooks, cron jobs, or cross-org jobs. Others need a security review to confirm they do not bypass organization isolation by mistake.

Realtime And Notifications

Several pages showed Supabase realtime websocket authentication failures in the browser console. This appeared on dashboard, calendar, IT, events, and mobile pages.

Why it matters: if realtime is broken, staff may not see ticket, message, or calendar updates without refreshing.

Fix: verify the Supabase browser auth token and realtime permissions. Also make sure failures are handled quietly if realtime is optional.

Best-Practice Benchmarks Used

I compared the product against common expectations for IT, maintenance, usability, and accessibility.

  • IT incident handling should help teams restore normal service quickly and keep status clear. Source: ITIL Incident Management by Axelos.
  • Maintenance work orders should capture description, asset, location, urgency, history, and backlog status. Source: MapTrack work order management guide.
  • Usability should keep people informed, use plain language, prevent errors, and stay consistent. Source: Nielsen Norman Group usability heuristics.
  • Accessibility should support keyboard use, visible focus, readable contrast, labels, and error help. Source: W3C WCAG 2.2 Understanding docs.

Fix Plan

First: make testing trustworthy

  • Fix smoke tests that still use old user fields.
  • Make all smoke scripts accept SMOKE_BASE_URL.
  • Add smoke:it and smoke:maintenance that test claim, assign, status, comment, photo/upload, and close flows.
  • Fix the E2E server workflow so build and dev do not fight over .next.

Second: speed up daily work

  • Use production-mode benchmarks for speed decisions. Local dev mode inflated the earlier API numbers.
  • Keep the broad k6 run as a map for suspicious areas, not as final production proof.
  • Keep reducing first-load JavaScript on any page that crosses about 300 kB. The first IT, IT admin, maintenance, dashboard, athletics, calendar, event detail, event day-of, form builder, and Events Hub passes are done.
  • Lazy-load admin-only tabs and charts.
  • Add query caching for dashboard and settings data that rarely changes.

Third: make IT and maintenance easier in the field

  • Create a focused “My work today” view for IT and maintenance workers.
  • Make claim, start, hold, complete, add note, add photo, and contact requester one-tap actions on mobile.
  • Show location, asset/device, requester, priority, due time, and last update at the top of every job detail.
  • Make the closeout step clear: work done, photos, labor/parts, notes, requester notification.

Fourth: fix accessibility

  • Fix color contrast on all flagged pages.
  • Fix hidden focus issues.
  • Name all buttons and progress bars.
  • Run the accessibility suite again on desktop and mobile.
