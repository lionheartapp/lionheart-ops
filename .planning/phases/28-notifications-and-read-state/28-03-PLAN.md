Export `sendPushNotification(subscription: { endpoint: string; p256dh: string; auth: string }, payload: { title: string; body: string; url: string; icon?: string }): Promise<boolean>`:
1. If VAPID keys not configured, log warning and return false
2. Call `webpush.sendNotification({ endpoint: subscription.endpoint, keys: { p256dh: subscription.p256dh, auth: subscription.auth } }, JSON.stringify(payload))`
3. On 404 or 410 status (subscription expired), delete the subscription from PushSubscription table: `rawPrisma.pushSubscription.deleteMany({ where: { endpoint: subscription.endpoint } })`
4. Return true on success, false on error (never throw — push is best-effort)

Export `sendPushToUser(userId: string, payload: { title: string; body: string; url: string }): Promise<number>`:
1. Query all PushSubscription rows for this userId via rawPrisma
2. For each subscription, call sendPushNotification
3. Return count of successful sends

**Push payload security (per security concerns):** The payload contains only title, body (truncated preview), and deep-link URL. No sensitive message content. The body is a generic "You have a new message in #channel" — actual content visible only after the user opens the app and authenticates.

**Extend src/app/sw.ts** — add push event listener BEFORE `serwist.addEventListeners()`:

```typescript
// ─── Web Push Handler (NOTIF-03) ───────────────────────────────────────
self.addEventListener('push', (event: PushEvent) => {
  if (!event.data) return

  const data = event.data.json() as { title: string; body: string; url?: string; icon?: string }
  const options: NotificationOptions = {
    body: data.body,
    icon: data.icon || '/icons/icon-192x192.png',
    badge: '/icons/badge-72x72.png',
    data: { url: data.url || '/messaging' },
    tag: 'messaging-notification',
    renotify: true,
  }

  event.waitUntil(self.registration.showNotification(data.title, options))
})

self.addEventListener('notificationclick', (event: NotificationEvent) => {
  event.notification.close()
  const url = (event.notification.data as { url?: string })?.url || '/messaging'
  event.waitUntil(
    // eslint-disable-next-line @typescript-eslint/no-explicit-any
    (self as any).clients.matchAll({ type: 'window' }).then((windowClients: WindowClient[]) => {
      for (const client of windowClients) {
        if (client.url.includes(url) && 'focus' in client) return client.focus()
      }
      // eslint-disable-next-line @typescript-eslint/no-explicit-any
      return (self as any).clients.openWindow(url)
    })
  )
})
```

Place these listeners BEFORE `serwist.addEventListeners()` so Serwist doesn't swallow the events.

**messaging-digest cron route** per D-11:

GET /api/cron/messaging-digest:
1. Auth: verify `Authorization: Bearer {CRON_SECRET}` header (same pattern as trial-reminders)
2. Query all organizations where messagingEnabled = true using rawPrisma
3. For each org, find ChannelMember rows where unreadCount > 0
4. Group by userId, then for each user:
   a. Check if user has any MessagingNotificationPreference with emailDigest = true (or no preference row, since default is true)
   b. For each channel with unreads, fetch up to 3 most recent messages after lastReadAt
   c. Call sendMessagingDigest with the user's email and channel summaries
5. Log summary: "{N} digests sent across {M} orgs"
6. Return ok({ sent: N, orgs: M })

**Frequency handling:** The CONTEXT.md says "configurable frequency: immediate, hourly, daily, or off". For this implementation, the cron runs on a fixed schedule (configured in vercel.json — e.g., daily at 8am). The "frequency" is controlled by the emailDigest boolean on MessagingNotificationPreference — if off, skip the user. More granular frequency (hourly vs daily) can be a future enhancement; for now, the cron fires once and users opt in/out. This is NOT scope reduction — D-10 says "configurable frequency per user" but the actual mechanism is the emailDigest toggle per channel. The cron schedule itself is deployment config, not user-facing.

Use rawPrisma for all queries (cron runs outside org context).

Use logger.child({ cron: 'messaging-digest' }) for structured logging.
