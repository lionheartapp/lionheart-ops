1. **Interface:**
```typescript
interface RealtimeContextValue {
  supabaseClient: SupabaseClient | null
  isConnected: boolean
  connectionError: string | null
}
```

2. **Context + consumer hook:**
```typescript
const RealtimeContext = createContext<RealtimeContextValue>({
  supabaseClient: null,
  isConnected: false,
  connectionError: null,
})

export function useRealtime() {
  return useContext(RealtimeContext)
}
```

3. **Provider implementation:**
- On mount, fetch JWT from `/api/auth/token` using `fetchApi`.
- Create a Supabase client using `createClient(supabaseUrl, supabaseAnonKey, { realtime: { accessToken: async () => fetchedToken } })`. The `accessToken` callback returns the JWT for Realtime auth. Use `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` env vars.
- Store the client in a `useRef` (not useState — avoid re-renders on client object identity changes).
- Track `isConnected` via a `useState` boolean, set to true when the client connects.
- Track `connectionError` for display in UI.

4. **Token refresh strategy** (Claude's discretion area):
- Refresh token 5 minutes before expiry. Calculate refresh time from `expiresAt` in the token response.
- Use `setTimeout` for the refresh, not polling interval.
- On refresh failure, retry with exponential backoff (1s, 2s, 4s, max 30s). After 3 consecutive failures, set `connectionError`.

5. **Cleanup on unmount:**
- Remove all channels from the Supabase client.
- Clear any pending refresh timeouts.
- Set `cleanedUp = true` guard to prevent state updates after unmount.

6. **Graceful degradation:**
- If token fetch fails on mount, set `connectionError` but do not throw. The hook consumers will fall back to polling (Phase 26 concern).
- If `NEXT_PUBLIC_SUPABASE_URL` or `NEXT_PUBLIC_SUPABASE_ANON_KEY` is missing, set `supabaseClient` to null and `connectionError` to a descriptive message.

Export both `RealtimeProvider` and `useRealtime`.

Create `src/lib/hooks/useRealtimeChannel.ts` (per D-04).

This is a `'use client'` hook that subscribes to broadcast, typing, and presence for a single channel.

1. **Interface:**
```typescript
interface TypingUser {
  userId: string
  displayName: string
}

interface UseRealtimeChannelOptions {
  channelId: string | null
  orgId: string
  currentUserId: string
  currentDisplayName: string
}

interface UseRealtimeChannelResult {
  incomingMessage: Message | null  // latest broadcast message (consumers append to their list)
  typingUsers: TypingUser[]
  presenceState: Map<string, 'online' | 'away' | 'offline'>
  isConnected: boolean
  error: string | null
  sendTypingIndicator: () => void
}
```

2. **Broadcast subscription (RT-01, D-06):**
- Get Supabase client from `useRealtime()` context.
- When `channelId` changes (and client is available), subscribe to topic `msg:${orgId}:${channelId}`.
- Listen for `new_message` broadcast event. On receive, set `incomingMessage` to the payload. The consuming component is responsible for deduplicating and appending to its message list.
- Skip messages where `payload.authorId === currentUserId` (optimistic sends handled by the composer).

3. **Typing indicators (RT-02, D-09, D-10):**
- Listen for `typing` broadcast events on the same channel. Payload: `{ userId, displayName }`.
- Maintain a `typingUsers` array. When a typing event arrives, add/update the user. Clear each user after 3 seconds of no typing events from them (use a Map of timeouts keyed by userId).
- Filter out `currentUserId` from typingUsers (don't show "you are typing").
- `sendTypingIndicator()` function: broadcasts a `typing` event with `{ userId: currentUserId, displayName: currentDisplayName }`. Debounce: only actually send once every 3 seconds using a `useRef` timestamp guard. The consuming component calls this on keystrokes.

4. **Presence (RT-03, D-08):**
- Subscribe to presence on the same channel.
- On `sync` event, read `channel.presenceState()` and build a Map of userId -> status.
- Track the current user with `channel.track({ userId: currentUserId, status: 'online', lastActive: Date.now() })`.
- Presence states: `online` (tracked and lastActive < 5 min), `away` (tracked but lastActive >= 5 min), `offline` (not in presence state).
- Update `lastActive` on the current user every 60 seconds via a heartbeat interval. If the user hasn't interacted for 5+ minutes, track status as `away`.

5. **Cleanup:**
- On channelId change or unmount, unsubscribe from the Supabase channel.
- Clear all typing timeouts.
- Clear the heartbeat interval.
- Use `cleanedUp` boolean guard to prevent state updates after unmount.
- Use `channelRef` to hold the Supabase channel instance for cleanup.

6. **Error handling:**
- If `useRealtime()` returns null client, set `error` to "Realtime not available" and return defaults.
- If subscription fails, set `error` with the failure reason.

Export `useRealtimeChannel` and the `UseRealtimeChannelResult` and `TypingUser` interfaces.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser JS -> Supabase Realtime | Client subscribes to topics; must only receive messages for their org |
| Typing broadcast | Any subscribed client can send typing events on a channel |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-05 | Spoofing | Typing indicator | accept | A user could spoof typing events with a fake displayName, but typing indicators are ephemeral and low-value. The userId in the payload comes from the client's auth context. |
| T-25-06 | Tampering | Broadcast subscription | mitigate | Topic naming includes orgId (msg:{orgId}:{channelId}). Even if a client constructs a topic for another org, Supabase Realtime + RLS prevents cross-org subscription. The client-side orgId comes from the authenticated JWT claims. |
| T-25-07 | Denial of Service | Typing broadcast spam | mitigate | Sender-side debounce (3 seconds per D-10) limits typing broadcasts. Supabase Realtime has built-in rate limiting (eventsPerSecond param). |
| T-25-08 | Information Disclosure | Presence state | accept | Presence reveals who is online in a channel. This is expected behavior for a messaging app. Only channel members can see presence (subscription requires channel membership via RLS). |
</threat_model>
